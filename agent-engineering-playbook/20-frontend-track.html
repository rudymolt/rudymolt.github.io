The Frontend Track

The frontend track helps you and your agent build a consistent user interface. It records the names, appearance and behaviour of UI elements in three shared design artefacts, so each feature builds on decisions already made.

The Three Design Artefacts

These three artefacts define the project's UI vocabulary, component styles and interaction patterns. Each answers a different design question.

The

The words. Every screen term — pill, container, primary button — is defined exactly once, so "pill" means the same thing to you, the agent, and the code.

The

The visual language. Every glossary term shown live on one page that opens in any browser — every approved colour, spacing, and on-screen building block, with nothing hidden away in the code.

The

How it behaves. The kitchen sink shows what a slide-in drawer looks like; the guide says when a drawer is the right answer — a simple table matching each job to the right (the kind of panel it appears in).
The hard rule: never invent new screen words or patterns. If a term is missing from the glossary, or a screen needs a the guide hasn't approved, the agent must stop, ask you to decide, and update the three files before writing any screen code. The files lead; the code follows.

Project Setup: The Setup Question

Start from a pinned public release and invoke /ai-playbook-bootstrap-project. It inspects the project, presents a read-only plan and dry-run, then applies only the approved UI, CI and host choices while preserving project-owned content.

During setup, choose whether to use the playbook's design templates, bring your own, or combine the two. The agent records your choice before applying it:

AgentThis project has a screen. How do you want to set up the three frontend design files (glossary, kitchen sink, design-language guide)?

1 · Use the playbook defaults — I copy all three starter templates, then run the design interview to adapt them to your brand.
2 · Supply your own — point me at existing files, a design tool export (such as Figma), screenshots, or a ready-made set of components, and I'll reshape them to fit the three files.
3 · Mix — defaults for some, your own for others.
4 · Skip for now — only if the project genuinely has no screen. I'll record that decision in so you aren't asked again every session.
YouUse the defaults — but our brand colour is teal, not gold.
AgentI'll include those choices in the dry-run. After you approve it, I'll apply the templates and record the design interview answers in the artefacts.

Setup must leave all three design artefacts in place, unless the project has no UI and records that exception. The starter kitchen sink includes tables, drawers, overlays and application layouts to give new projects a useful starting point.

The Design Interview

If the project has no design system, the agent runs a . Its eleven questions cover colour, typography, spacing, components, interaction and accessibility, including which screen sizes to support and when to use rows, cards, drawers or modals.

Record every answer in the appropriate design artefact: a glossary entry, a component or style in the kitchen sink, or an interaction rule in the design-language guide. Future sessions need to find these decisions in project files.

How the frontend track fits the workflow

The vocabulary source may be DESIGN-GLOSSARY.md or a split design-glossary/. Read the generated index first, then only the entries needed.

The frontend track is not a separate process — it adds one screen-related check to each stage of the 13-stage map:

  • Prerequisites (00). Check the three files exist. Missing, with no recorded decision to skip? Stop and run the setup question.
  • Align (01). After pressure-testing a feature that affects the screen, show an ASCII sketch and get approval. For interactive or non-trivial UI, then make and approve a clickable (a preview of the screen) using the project's visual language — choosing panels by the guide's rules.
  • Context (02). New style values go into the kitchen sink, new terms into the glossary, new ways of behaving into the guide.
  • Breakdown (04). Each small piece of screen work (a ) names the glossary terms it uses in its pass/fail conditions.
  • Architecture (06). Check for drift: any style in the code that isn't in the kitchen sink is a shortcut to be tidied up later; any pop-up doing a slide-in panel's job breaks the guide.
  • Implementation (07). Code uses only glossary terms, only kitchen-sink styles, only approved panels.
  • Review (08) & QA (09). Every change that touches the screen passes the below.

The UI Smoke Floor

/ai-playbook-design-review and report-only browser QA produce evidence. Accepted findings go to a separate builder task, then fresh Verify; auto-fixing QA cannot certify its own changes. Direct upstream reviewers first need an exact-source, report-only compatibility check.

Every piece of screen work must pass this floor before it ships.
